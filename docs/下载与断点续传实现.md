# 下载与断点续传实现

## 1. 请求处理流程

```
客户端请求
  ↓
proxyDownloadRequest
  ├─ 创建转发请求 + 复制请求头 + 修正 Content-Length
  ├─ 应用 token
  ├─ [可选] 并发 Range 预检（获取文件总大小）
  ├─ 发送请求到 GitHub
  ├─ 安全检查（Content-Type 过滤 + 文件大小上限）
  └─ 分发
       ├─ .sh / .ps1 → handleScriptResponse（URL 替换）
       └─ 其他       → handleNormalResponse → 流式输出
```

核心代码：`handlers/proxy_download.go`。

## 2. 下载模式

### 2.1 标准模式（默认）

```
1. 并发执行两个请求：
   - Range bytes=0-0 → Content-Range: bytes 0-0/总大小 → 得到总大小
   - 实际下载请求 → 等待响应
2. 两个请求并行，预检结果设置 Content-Length → 浏览器显示进度条
3. 流式输出到客户端
```

适用：Release 大文件、需要进度反馈的下载。

### 2.2 快速模式（`?fast=1`）

跳过 Range 预检，直接下载。无进度条但响应更快。

适用：主分支 ZIP、小文件。

### 2.3 断点续传（客户端带 `Range` 头）

当客户端（浏览器或下载工具）已经拥有文件的前半部分，只想下载剩余部分时，发送带 `Range` 头的请求。代理透视此行为，不做额外处理。

**检测**（`proxy_download.go:105`）：

```go
isRangeRequest := c.Request.Header.Get("Range") != ""
```

`Range` 非空即视为续传请求。

**完整流序**：

```
客户端已下载 0-1023 字节，现在请求剩余：
  GET /.../file.zip
  Range: bytes=1024-

    ↓ 代理检测到 Range 头 → isRangeRequest=true
    
    ↓ 跳过 Range 预检
      （续传不需要总大小，只需要本次传输量）
    
    ↓ 透传 Range 到 GitHub
      GET https://github.com/.../file.zip
      Range: bytes=1024-
    
    ↓ GitHub 返回
      HTTP 206 Partial Content
      Content-Range: bytes 1024-9999/10000   ← 本次范围 / 总大小
      Content-Length: 8976                    ← 本次传输的字节数
      
    ↓ handleNormalResponse(isRangeRequest=true)
      knownSize = 8976（取 Content-Length，即剩余字节数）
      
    ↓ writeResponse
      Status: 206（透传）
      Content-Length: 8976（透传，不覆盖）    ← 关键：不设总大小
      Content-Range: bytes 1024-9999/10000（透传）
      流式输出 8976 字节
      
    ↓ 客户端收到
      将 8976 字节追加到已有 1024 字节后 → 完整 10000 字节文件
```

**关键规则**：

```go
// 206 响应不覆盖 Content-Length，使用 GitHub 返回的剩余大小
if knownSize > 0 && resp.StatusCode != http.StatusPartialContent {
    c.Header("Content-Length", strconv.FormatInt(knownSize, 10))
}
// 206 时 knownSize = GitHub 返回的 Content-Length（已透传），所以不执行上面的 if
```

| | 首次下载（200） | 断点续传（206） |
|:---|:---|:---|
| Range 预检 | 执行（并发，获取总大小） | 跳过（不需要） |
| 发给 GitHub 的 Range | 不发送 | 透传客户端的 Range |
| GitHub 返回 | 200 + Content-Length=总大小 | 206 + Content-Range + Content-Length=剩余大小 |
| 代理设置的 Content-Length | 总大小（来自预检或响应） | 不设置（透传 GitHub 的剩余大小） |
| 客户端看到的 Content-Length | 总大小 → 进度条正常 | 剩余大小 → 续传数据量正确 |
| 响应体 | 完整文件 | 指定范围的字节 |

**为什么跳过预检？**

续传请求的 `Range: bytes=1024-` 已经指定了想要的范围。如果再做一次 `Range: bytes=0-0` 预检：
1. 浪费一次 HTTP 往返
2. 预检结果（总大小）对续传无用——客户端已经有前半部分，需要的是剩余大小
3. GitHub 的 206 响应中 `Content-Length` 就是剩余大小，直接透传即可

**为什么不能覆盖 Content-Length？**

如果代理把 206 响应的 Content-Length 改为预检得到的总大小（10000），客户端收到 10000 字节的 Length 头，但实际只收到 8976 字节——下载工具会认为连接中断或数据损坏，导致续传失败。

因此规则是：`206 → 完全不碰 Content-Length，GitHub 给什么就透传什么`。

## 3. 文件大小探测

实现：`internal/service/github/download/size_probe.go`。

### 方式一：Range 探测

```go
// 发送 Range: bytes=0-0
// 206 Partial Content → Content-Range: bytes 0-0/总大小
// 200 OK           → Content-Length 头获取大小
```

适用于 GitHub Releases CDN（均支持 Range 响应）。与真实下载并发执行，不增加延迟。失败返回 0，降级为 chunked 传输。

### 方式二：API 查询

```go
// 从 URL 提取 owner/repo/tag
// 调用 api.github.com/repos/{owner}/{repo}/releases/tags/{tag}
// 累加所有 asset.size
```

适用于 `/archive/refs/tags/...` 和 `codeload.github.com` 链接（Archive 通常不支持 Range）。

三级调度 `PrefetchContentLength()`：

```go
if size := RangeProbeSize(); size > 0 { return size }
if IsArchiveURL(url) { return QueryArchiveSizeFromAPI() }
return 0 // 全部失败 → chunked 传输
```

## 4. Content-Length 设置策略

`handleNormalResponse` 根据场景选择不同来源：

| 场景 | Content-Length 来源 |
|:---|:---|
| 首次下载，预检成功 | 预检获得的总大小 → 浏览器显示进度条 |
| 首次下载，预检失败 | GitHub 响应的 Content-Length 或 Content-Range 总大小 |
| 断点续传（206） | 不覆盖，使用 GitHub 返回的剩余大小 |
| 全失败（chunked） | 不设置，无进度条但可正常下载 |

```go
if isRangeRequest {
    // 透传 GitHub 的 Content-Length（剩余部分）
    knownSize = resp.Content-Length
} else {
    // 首次下载：预检 > Content-Length > ContentRange
    knownSize = preflightSize ?? resp.Content-Length ?? Content-Range total
}
```

## 5. 安全检查

### Content-Type 过滤

阻止网页内容被代理，仅对 GET 检查：

```
text/html, application/xhtml+xml, text/xml, application/xml
→ 403 "检测到网页类型，本服务不支持加速网页"
```

### 文件大小限制

```
Content-Length > fileSize（默认 2GB）
→ 413 "文件过大"
```

配置：`config.toml` → `[server].fileSize` 或 `MAX_FILE_SIZE`。

## 6. 脚本文件处理

`.sh` / `.ps1` 文件内部所有 `github.com` / `githubusercontent.com` 链接自动替换为代理地址。

实现：`internal/service/github/download/script_processor.go`。

```
原：curl -L https://github.com/user/repo/releases/download/v1.0/tool.sh
后：curl -L https://hub.example.com/https://github.com/user/repo/releases/download/v1.0/tool.sh
```

细节：
- 正则匹配所有 `https?://github.com|raw.githubusercontent.com|...` 链接
- 自动检测 gzip 压缩（magic bytes `0x1f 0x8b`）
- 上限 10MB，超过拒绝
- 无 GitHub 链接时原样返回，零开销

## 7. 流式输出

`handlers/response_writer.go` 负责将 GitHub 响应流式写入客户端。

**渐进式 Flush**：每 64KB 调用 `http.Flusher.Flush()`，数据立即可达。

**水位线反压 + 限速** 详见 [下载限速与稳定性设计](下载限速与稳定性设计.md)。

## 8. POST 请求（Git Push）

对于 POST 请求（git push 等），`Content-Length` 从原始客户端请求复制到转发请求，避免 Go HTTP 客户端回退为 chunked 编码：

```go
if c.Request.ContentLength > 0 {
    req.ContentLength = c.Request.ContentLength
}
```
