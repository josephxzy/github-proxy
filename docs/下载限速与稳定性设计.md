# Go 程序限速与下载稳定性优化方案

> **当前状态**：第 8 节描述的两层写入限速 + 水位线反压均已实现。SO_RCVBUF 已设为 4MB。配置项 `bufferSize` / `downloadBytesPerSec` / `globalBytesPerSec` 可直接使用。

## 1. 架构全景

系统分为四层：

```
用户A (限速 2MB/s) ──┐
用户B (限速 5MB/s) ──┤
用户C (无限制)     ──┼──→ [Go 程序] ──→ [操作系统内核] ──→ GitHub (全速 50MB/s)
                     │    ▲                  ▲
                     │    │                  │
                per-user           SO_RCVBUF 4MB
              token bucket        (内核 TCP 缓冲区)
```

核心矛盾一目了然：GitHub 以 50MB/s 灌数据，用户加起来可能只需要 10MB/s。操作系统内核不会帮我们做限速——它的职责就是尽最大努力收发数据。限速必须在 Go 程序层完成。

如果只做用户侧限速、任操作系统全速收包，结果就是内核缓冲区被 50MB/s 的数据迅速填满，TCP 窗口归零，连接中断。

## 2. 双层限速机制

Go 程序内部通过两层机制共同工作：

```
              ┌─────────── 水位线（per-file）───────────┐
              │  暂停 Read() at 80%   恢复 at 20%        │
              │  （生产者端，每文件独立）                  │
              ▼                                          ▼
File A ──→ [缓冲A+水位A] ──┐
File B ──→ [缓冲B+水位B] ──┤
File C ──→ [缓冲C+水位C] ──┼──→ [用户X token bucket] ──→ 用户X
                            ├──→ [用户Y token bucket] ──→ 用户Y
                            └──→ [用户Z 不限速]      ──→ 用户Z
```

| 层 | 位置 | 机制 | 作用 |
|:---|:---|:---|:---|
| **用户侧** | 写入端 | per-user token bucket | 每个用户独立的下载上限 |
| **水位线** | 读取端（per-file） | 80%/20% 暂停/恢复 | 防止单文件内部缓冲区溢出，倒逼 TCP 流控 |

### 为什么不需要全局读 token bucket？

producer goroutine 的执行是 `Read → Write → 检查水位 → 决定暂停`，全部内联在同一条 goroutine 里。每次只读 32KB，50MB/s 下每循环仅 0.6ms——水位检查完全在单次调度内完成，不存在"goroutine 来不及暂停"的问题。

加上全局读 token bucket 反而有害：它把不同文件的读取放在同一个队列里竞争 token。现实经验是 GitHub CDN 对不同文件的速度分配极不均匀——一个文件跑到 50MB/s，另一个可能只有 3MB/s。全局 bucket 会让快文件"占着茅坑"（持有 token 但已暂停），慢文件即使有带宽余量也拿不到 token。

**去掉全局 bucket，每文件只靠自己的水位线**，快文件自然高频暂停、释放带宽，慢文件自然流畅读取——无需人工调度。

## 3. 水位线停止/恢复的完整流序

### 阶段一：正常下载中

```
内部缓冲区 ████████░░░░░░░░░░  35%
       │
       ├─→ 从内核全速或自然速度读取（50MB/s）
       └─→ 多个用户 token bucket 控制向各用户写入速度（合计 10MB/s）
       
净流入 = 50 - 10 = 40MB/s → 缓冲区快速增长
但每次只读 32KB，读完立刻检查水位，涨到 80% 立即暂停
```

### 阶段二：触达高水位 → 暂停读取

```
内部缓冲区 ████████████████░░  80%  → 触发高水位
       │
       └─→ Go 程序停止调用 resp.Body.Read()
           但内核缓冲区中还有已接收的数据
           GitHub 也还不知道要暂停——仍有飞行数据在路上

内核层：
        GitHub ──飞行数据(2.5MB)──→ [内核缓冲区 ████████░░]
        
        内核缓冲区继续向内部缓冲区吐数据（Go 还没来取）
        同时 GitHub 的飞行数据还在往内核缓冲区灌

Go 层：
        停止 Read() 的瞬间，内部缓冲区可能微涨到 85%~90%
        这多出来的 5%~10% 就是内核缓冲区里积压的数据
```

### 阶段三：用户消费，缓冲区下降

```
内部缓冲区 ██████████░░░░░░░░  50%
       │
       └─→ 用户 token bucket 持续消费（合计 10MB/s）
           此时没有新数据进来，缓冲区只出不进
```

### 阶段四：触达低水位 → 恢复读取

```
内部缓冲区 ████░░░░░░░░░░░░░░  20%  → 触发低水位
       │
       └─→ Go 程序恢复调用 resp.Body.Read()

恢复瞬间：
        内核缓冲区可能已经排空或接近排空
        TCP 窗口重新打开 → 通知 GitHub 可以继续发送
        
        GitHub 数据需要 RTT(50ms) 才能到达
        在这 50ms 空窗期内，用户仍在消费
        内部缓冲区可能从 20% 继续降到 ~15%
        
        RTT 过后 → GitHub 数据到达 → 缓冲区开始重新上涨
```

### 完整循环

```
 80%  ┤         ╱╲          ╱╲
      ┤        ╱  ╲        ╱  ╲
      ┤       ╱    ╲      ╱    ╲       ← 暂停读取,
 50%  ┤──────╱      ╲────╱      ╲────    缓冲区下降
      ┤     ╱        ╲  ╱        ╲
      ┤    ╱          ╲╱          ╲
 20%  ┤───╱            ╲            ╲── ← 恢复读取,
      ┤  ╱              ╲            ╲    GitHub 数据到达
      ┤ ╱ 读取(自然速度)  ╲ 暂停       ╲
      ┤╱  写入(10MB/s)    ╲ 写入(10MB/s)╲
     ─┴────────────────────────────────────→ 时间
        填充             排空           填充
```

关键点：缓冲区在 20%-80% 之间振荡，TCP 窗口**永远不会归零**。飞行数据被内核 `SO_RCVBUF`（4MB）和内部缓冲区的剩余 20% 空间共同吸收。

## 4. 参数设计

### 核心参数

| 参数 | 推荐值 | 计算依据 |
|:---|:---|:---|
| 内部缓冲区 | 4MB | > 飞行数据量（50MB/s × 0.05s = 2.5MB），留有安全余量 |
| 高水位 | 80%（3.2MB） | 剩余 20%（0.8MB）+ 内核 SO_RCVBUF（4MB）= 4.8MB 可吸收飞行数据 |
| 低水位 | 20%（0.8MB） | 恢复后有足够数据支撑 RTT 空窗期（50ms × 10MB/s = 0.5MB） |
| SO_RCVBUF | 4MB | 内核层吸收飞行数据，防止 Window 直接归零 |

### 低水位为什么是 20% 而不是 0%？

如果在 0% 才恢复读取，用户会经历一段"无数据可发"的空等期——RTT 50ms 内 GitHub 数据还没到，内部缓冲区又是空的，所有用户 token bucket 都处于饥饿状态。

20% 的低水位确保恢复后至少还有 0.8MB 数据在缓冲区中，足以支撑 50ms 的空窗期（10MB/s × 0.05s = 0.5MB < 0.8MB）。

### 高水位为什么是 80% 而不是 100%？

暂停 `Read()` 之后：

1. 内核缓冲区里还有已接收但未被 Go 读取的数据
2. GitHub 还在持续发送（RTT 时间内不知道要暂停）

这两股数据会在暂停瞬间继续涌入内部缓冲区。如果高水位设在 100%，就没有余量吸收这波涌入——缓冲区溢出，或者内核缓冲区溢出，TCP 窗口归零。

80% 的设定让 20% 余量（0.8MB）+ `SO_RCVBUF`（4MB）吸收暂停后的飞行数据。

## 5. 实际场景：两个速度都是未知的

前面的计算用了 50MB/s、10MB/s 等具体数字，但真实环境中：

| 变量 | 实际特征 | 我们能控制什么 |
|:---|:---|:---|
| GitHub → 服务器速度 | 未知。取决于 GitHub CDN、服务器带宽、中间路由。可能是 5MB/s，也可能是 100MB/s。**无法指定**。 | 什么都控制不了。操作系统会以链路最大能力接收。 |
| 服务器 → 用户速度 | 未知。取决于每个用户的网络环境。有人 500KB/s，有人 10MB/s。**无法指定**。 | 只能设**上限**（token bucket ceiling），用户实际速度 = min(上限, 自身网速) |

### 两个"无法指定"意味着什么？

**GitHub 侧**：我们没办法告诉 GitHub "慢点发"。GitHub 发多快取决于它那边的网络条件。今天 50MB/s，明天可能 20MB/s，后天 100MB/s。

**用户侧**：我们没办法让用户"快点收"。token bucket 设 5MB/s 上限，用户实际跑到 500KB/s 是因为他家宽带就这速度——token bucket 对他完全是透明的，永远不会触发限速。

### 为什么水位线仍然有效？

水位线是一个**反馈闭环**，不是前馈计算。它不看速度数字，只看一个东西：**缓冲区的当前水位**。

```
缓冲区高了？ → 暂停读取。  （不管 GitHub 是多快导致的高水位）
缓冲区低了？ → 恢复读取。  （不管用户是多慢导致的低水位）
```

这意味着它对任何速度组合都是自适应的：

| 场景 | GitHub 速度 | 用户总消耗 | 缓冲区行为 | 水位线动作 |
|:---|:---|:---|:---|:---|
| 理想 | 50MB/s | 10MB/s | 快速上涨 | 正常暂停/恢复循环 |
| GitHub 慢 | 8MB/s | 10MB/s | 始终低位 | 永不暂停（无需限速） |
| GitHub 快 | 100MB/s | 3MB/s | 极速上涨 | 频繁暂停，水位线每 0.3ms 检查一次完全够用 |
| 凌晨无人 | 50MB/s | 0 | 快速上涨 | 暂停后长期挂起，TCP 窗口保活 |
| 高峰多人 | 50MB/s | 40MB/s | 缓慢上涨 | 偶尔暂停，大部分时间通畅 |

### 多文件时的不均匀速度

实际使用中有个经验现象：从 GitHub 同时下载多个文件时，速度往往极不均匀——一个文件跑到 50MB/s，另一个只有 3MB/s。这是 GitHub CDN 的常态：不同文件可能来自不同边缘节点，TCP 拥塞控制对低 RTT 连接更"慷慨"。

**水位线完美适配这种不均匀**：快文件的缓冲区高频暂停/恢复，慢文件自然流畅，互不干扰。因为每个文件的水位线**只管自己**——快文件暂停时不占用任何全局资源，慢文件照常读取。

### 用户过多、每人达不到上限怎么办？

per-user token bucket 设的是**上限**，不是**保证**。

```
假设：服务器从 GitHub 总共能拉到 50MB/s
      10 个用户，每人的 token bucket 上限 = 10MB/s（合计 100MB/s）
      
实际：每个用户能分到的 ≈ 50 / 10 = 5MB/s（远低于 10MB/s 上限）
```

这完全正常——token bucket 没有触发限速，token 永远充裕。用户实际速度由"服务器能拉多快 / 用户数"决定，token bucket 只是防止个别用户独占全部带宽。**上限设得宽松反而更好**：它只在少数大流量用户同时下载时才出手截流，平时所有人顺畅。

### 缓冲区大小是否要动态调节？

**不需要。** 原因有三：

1. **水位线是反馈机制，不是前馈**。它不关心"GitHub 实际是多快"，只看"缓冲区现在多满"。GitHub 100MB/s 还是 10MB/s，水位线照常工作。

2. **缓冲区只要 ≥ 飞行数据量即可**，飞行数据量 = 实际带宽 × RTT。如果服务器到 GitHub 的实际带宽只有 10MB/s，飞行数据 = 0.5MB——4MB 缓冲区绰绰有余。如果带宽是 1Gbps（125MB/s），飞行数据 = 6.25MB——4MB 偏小，需要调到 8MB 以上。

3. **调大不调小**。缓冲区设大（比如 8MB）的唯一代价是多占一点内存；设小的代价是 TCP 窗口可能归零导致断连。所以取一个"覆盖绝大多数场景"的固定值即可。

**建议**：取服务器实际带宽 × RTT × 2 作为**下限**，然后往上调到不再高频震荡为止。管理员根据自己服务器的网络条件配置一次即可，不需要运行时动态调整。

实现上作为 `config.toml` 的配置项，提供保守默认值：

```toml
[server]
# 每文件内部缓冲区大小（字节），用于水位线反压
# 默认 8MB，适用于 500Mbps 以下带宽；1Gbps 以上建议 16~32MB
bufferSize = 8388608
```

环境变量 `BUFFER_SIZE` 可覆盖。

缓冲区过小的代价不是溢出——水位线能兜底——而是"填满-暂停-排空-恢复"的循环太快。50MB/s 带宽 + 4MB 缓冲区 + 零用户时，一次填充仅 0.05 秒，连接在暂停/恢复之间每秒跳变 10+ 次，有效吞吐率反而下降。调大缓冲区让每次振荡周期至少几百毫秒：

| 服务器带宽 | 飞行数据 | 仅满足下限 | 下限的问题 | **推荐** | 推荐的理由 |
|:---|:---|:---|:---|:---|:---|
| 100Mbps（~12MB/s） | 0.6MB | 2MB | 无用户时填充 0.08s → 高频震荡 | **8MB** | 填充 0.32s，够用 |
| 500Mbps（~60MB/s） | 3MB | 4MB | 无用户时填充 0.05s → 剧烈震荡 | **16MB** | 填充 0.2s |
| 1Gbps（~125MB/s） | 6.25MB | 8MB | 无用户时填充 0.04s → 剧烈震荡 | **32MB** | 填充 0.15s |

## 6. 多文件并发：每文件独立水位线

当多个用户同时下载**不同文件**时，每个文件有自己的 HTTP 连接、独立的 `resp.Body`、独立的内核缓冲区，因此需要**每文件一个 producer goroutine + 独立 WaterlineBuffer**。

```
File A ──→ [缓冲A + 水位A] ──┐
File B ──→ [缓冲B + 水位B] ──┤
File C ──→ [缓冲C + 水位C] ──┼──→ [用户X bucket] ──→ 用户X
                              ├──→ [用户Y bucket] ──→ 用户Y
                              └──→ [用户Z 不限速]  ──→ 用户Z
```

| 场景 | File A | File B | 结果 |
|:---|:---|:---|:---|
| 两个都快 | 缓冲→80% 暂停 | 缓冲→80% 暂停 | 各自独立暂停/恢复，互不影响 |
| A 快 B 慢 | 缓冲→80% 暂停 | 缓冲低位，持续读 | B 不受 A 暂停影响 |
| A 暂停中 B 启动 | 保持暂停 | 从 0% 开始填充 | B 正常启动，A 等待用户消费 |
| A GitHub 慢(3MB/s) | 缓冲低位 | — | 水位线永不触发，无需限速 |

关键点：**每个文件的水位线只管自己那块缓冲区**，不需要全局 token bucket 来"分配"带宽。因为 producer goroutine 内 Read/Write/Check 是内联的，每 0.6ms 检查一次水位，快速文件自然高频暂停、释放资源，慢速文件不受任何阻挡。

## 7. Go 实现

```go
package proxy

import (
	"context"
	"io"
	"net"
	"net/http"
	"sync"
	"syscall"
	"time"

	"golang.org/x/time/rate"
)

const (
	rcvBuf         = 4 * 1024 * 1024  // 内核 TCP 接收缓冲区
	internalBufCap = 4 * 1024 * 1024  // 内部缓冲区
	highWaterMark  = 0.8              // 高水位 80%
	lowWaterMark   = 0.2              // 低水位 20%
)

// WaterlineBuffer 带水位线的环形缓冲区
type WaterlineBuffer struct {
	mu        sync.Mutex
	data      []byte
	writePos  int
	readPos   int
	capacity  int
	cond      *sync.Cond // 用于通知暂停/恢复
	paused    bool
}

func NewWaterlineBuffer(capacity int) *WaterlineBuffer {
	b := &WaterlineBuffer{
		data:     make([]byte, capacity),
		capacity: capacity,
	}
	b.cond = sync.NewCond(&b.mu)
	return b
}

func (b *WaterlineBuffer) usage() float64 {
	return float64(b.writePos-b.readPos) / float64(b.capacity)
}

func (b *WaterlineBuffer) Write(data []byte) int {
	b.mu.Lock()
	defer b.mu.Unlock()
	n := copy(b.data[b.writePos:], data)
	b.writePos += n
	b.cond.Signal() // 通知消费者有新数据
	// 触达高水位 → 暂停上游读取
	if b.usage() >= highWaterMark && !b.paused {
		b.paused = true
	}
	return n
}

func (b *WaterlineBuffer) Read(p []byte) int {
	b.mu.Lock()
	defer b.mu.Unlock()
	for b.writePos <= b.readPos {
		b.cond.Wait()
	}
	n := copy(p, b.data[b.readPos:b.writePos])
	b.readPos += n
	// 降到低水位 → 恢复上游读取
	if b.usage() <= lowWaterMark && b.paused {
		b.paused = false
		b.cond.Broadcast()
	}
	b.compact()
	return n
}

func (b *WaterlineBuffer) ShouldPause() bool {
	b.mu.Lock()
	defer b.mu.Unlock()
	return b.paused
}

func (b *WaterlineBuffer) WaitWhilePaused() {
	b.mu.Lock()
	defer b.mu.Unlock()
	for b.paused {
		b.cond.Wait()
	}
}

func (b *WaterlineBuffer) compact() {
	if b.readPos > 0 && b.readPos == b.writePos {
		b.readPos = 0
		b.writePos = 0
	}
}

// NewHTTPClient 创建配置了 SO_RCVBUF 的 HTTP 客户端
func NewHTTPClient() *http.Client {
	dialer := &net.Dialer{
		Timeout: 30 * time.Second,
		Control: func(network, address string, c syscall.RawConn) error {
			return c.Control(func(fd uintptr) {
				syscall.SetsockoptInt(int(fd), syscall.SOL_SOCKET, syscall.SO_RCVBUF, rcvBuf)
			})
		},
	}
	return &http.Client{
		Transport: &http.Transport{DialContext: dialer.DialContext},
	}
}

// StreamWithRateLimit 带水位线 + per-user 限速的流式下载
//  - userLimiter: 该用户的 token bucket（nil 表示不限速）
//  - buf: 该文件独立的内部缓冲区
func StreamWithRateLimit(
	ctx context.Context,
	resp *http.Response,
	userLimiter *rate.Limiter,
	buf *WaterlineBuffer,
	w io.Writer,
) error {
	// 生产者：从 GitHub 全速读取 → 写入内部缓冲区
	// 受水位线控制
	producerDone := make(chan error, 1)
	go func() {
		defer close(producerDone)
		chunk := make([]byte, 32*1024)
		for {
			select {
			case <-ctx.Done():
				return
			default:
			}
			// 水位线暂停
			buf.WaitWhilePaused()

			n, err := resp.Body.Read(chunk)
			if n > 0 {
				buf.Write(chunk[:n])
			}
			if err == io.EOF {
				return
			}
			if err != nil {
				producerDone <- err
				return
			}
		}
	}()

	// 消费者：从内部缓冲区读取 → token bucket 限速 → 写入用户
	out := make([]byte, 32*1024)
	for {
		n := buf.Read(out)
		if n > 0 {
			if userLimiter != nil {
				if err := userLimiter.WaitN(ctx, n); err != nil {
					return err
				}
			}
			if _, err := w.Write(out[:n]); err != nil {
				return err
			}
		}
		select {
		case err := <-producerDone:
			return err
		default:
		}
	}
}
```

## 8. 当前实现

### 完整管道

```

  (GitHub)     全速读取，受水位     80%/20% 暂停/恢复
```

### 两层限速的协作方式

`rateLimitedWriter.Write()` 对每次写入依次过两道限速：

```go
func (w *rateLimitedWriter) Write(p []byte) (int, error) {
    n := len(p)
    if w.user != nil { w.user.wait(n) }   // ① per-user 漏桶
    if w.global != nil { w.global.wait(n) } // ② global 令牌桶
    return w.writer.Write(p)
}
```

| | per-user 限速器 | global 限速器 |
|:---|:---|:---|
| 算法 | 漏桶（独立，每请求一个） | 共享令牌桶（全局单例） |
| 作用 | 限制单个用户的峰值 | 限制所有未认证用户的总带宽 |
| 资源 | 每个下载流独占一个 | 所有下载流竞争同一个令牌池 |

**为什么不是简单的延迟相加？**

per-user 漏桶执行 `wait(n)` 期间，global 令牌桶在后台持续累积令牌。per-user 延迟结束后，global 通常已有足够令牌，无需额外等待。

只有在全局带宽真正被打满时——即所有用户的总消耗超过了 `globalBytesPerSec`——global 令牌池才会耗尽，后续写入才需要等待令牌恢复。

```
场景1：1 个用户，per-user=5MB/s，global=50MB/s
  user.wait(32KB) = 0.006s → global 令牌充足 → 无额外等待 → 速率 5MB/s ✓

场景2：20 个用户，per-user=5MB/s，global=50MB/s
  每人 user.wait(32KB) = 0.006s → global 令牌被 20 人抽干 → 每人 global.wait 额外 0.006s
  → 有效速率 ≈ 2.5MB/s，总计 50MB/s ✓
```

### 白名单免限速

`getDownloadLimiter` 检查 `authenticated` 标志。白名单用户（token 在 `TOKEN_WHITELIST` 中）创建的 `rateLimitedWriter` 不带任何限速器，直接透传。

## 9. 总结

| 如果只做... | 会发生什么 | 怎么办 |
|:---|:---|:---|
| 用户侧 token bucket | 内核缓冲区灌满 → TCP Zero Window → 断连 | 加上 per-file 水位线 |
| 双层全开 | 缓冲区在 20%~80% 振荡，TCP 窗口永不为零 | ✅ |
| GitHub 变慢或用户变少 | 缓冲区自然低位，水位线不触发 | ✅ 自适应，无需调参 |
| GitHub 变快或用户变多 | 暂停/恢复频率自动调整 | ✅ 自适应，无需调参 |
| 多文件速度不均 | 快文件高频暂停，慢文件流畅，互不干扰 | ✅ 每文件独立水位线 |

核心原则：**用户限速设上限（per-user token bucket）→ 单文件水位线兜底（per-file 80%/20%）**。水位线是纯反馈闭环，每文件独立运行，不依赖任何速度假设，不需要全局协调，无论 GitHub 和用户的网络条件如何变化，TCP 窗口都不会归零。
